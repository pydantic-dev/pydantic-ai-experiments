Guardrails: InputGuardrail checks only the user prompt (a block becomes a refusal and costs no tokens); OutputGuardrail can block (raising OutputBlocked), replace or retry; ToolGuardrail checks tool arguments before running and results before the model sees them. Guards return a bool or GuardrailResult and chain, so put redactors first. Permissions has modes 'full' (asks nothing), 'auto' (asks for risky commands such as rm -rf, git push, sudo and installs) and 'read-only'; pair it with HandleDeferredToolCalls and ask_permissions for an interactive approve prompt, and pass it to SubAgents via shared_capabilities. Second-model patterns recur across the Harness: ToolCallJudge blocks, ApprovalReviewer approves, TrajectoryJudge steers, Advisor consults, ModelRouter picks. PromptInjectionDefender scans tool results from email, web or tickets. Remember that guardrails are not isolation: real isolation is a sandbox, preferably a VM. Budgets: core UsageLimits caps one run; SpendLimits adds windows per run, conversation, day or month, per tenant, with Redis or Postgres stores across workers. It refuses the next request after a window is spent, so concurrent runs can overshoot slightly. ToolBudgets, ReportRemainingBudget, WrapUpAtLimits and DetectLoops are soft controls that keep a run alive and returning partial work.
