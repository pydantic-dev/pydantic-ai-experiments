Capabilities: v2’s unit of reusable behaviour

refunds = Capability(
    id='refunds',
    description='Refund eligibility and status.',
    instructions='Confirm the order ID first.',
    defer_loading=True,  # loaded on demand
)

@refunds.tool_plain
def refund_status(order_id: str) -> str:
    """Look up the refund status."""
    return f'Order {order_id}: refunded.'

agent = Agent('anthropic:claude-sonnet-5-5',
    capabilities=[refunds, Thinking('high'), Caching(),
        WebSearch(local='duckduckgo')])

Pydantic AI Field Guide · Capabilities · docs/capabilities/overview.md, docs/capabilities/on-demand.md

A capability (AbstractCapability) can contribute a toolset, native tools, instructions, model settings, a model choice, wrapper toolsets and models, and lifecycle hooks. Capability(...) is the shorthand when you don’t need a subclass. Many old Agent keyword arguments became capabilities in version 2: builtin_tools became NativeTool, prepare_tools became PrepareTools, history_processors became ProcessHistory, instrument became Instrumentation. Provider-adaptive capabilities (WebSearch, WebFetch, ImageGeneration, XSearch, MCP) use the provider’s native tool where the model supports it, and a local fallback otherwise, so you can write the agent once and run it on any provider. With defer_loading=True and a stable id, a capability collapses to one catalog line until the model calls load_capability(id=...), at which point its instructions, tools, settings and hooks go live. That is how Markdown skills work. Other core capabilities: PrepareTools, PrefixTools, SetToolMetadata, ProcessEventStream, ReinjectSystemPrompt, RaiseContentFilterError, SelectModel, ResolveModelId, FileUnderstanding, UseThreadExecutor, BatchModelRequests, HandleDeferredToolCalls, LocalWorkspace, and provider compaction. Built-in capabilities have fixed ids; one passed to run() replaces the agent’s.
