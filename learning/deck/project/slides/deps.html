Dependencies and instructions, injected per run

@dataclass
class Deps:
    user: str
    http: httpx.AsyncClient

agent = Agent('test', deps_type=Deps,
    instructions="Use the customer's name.")

@agent.instructions  # re-run before every request
def who(ctx: RunContext[Deps]) -> str:
    return f"The user's name is {ctx.deps.user}."

@agent.tool
async def lookup(ctx: RunContext[Deps], q: str) -> str:
    r = await ctx.deps.http.get(URL, params={'q': q})
    return r.text

  • deps: DB pools, HTTP clients, keys, tenant IDs. No globals.
  • Instructions are static, dynamic (@agent.instructions) or per run. Prefer them to system_prompt.
  • on_change='append' adds changes as a delta, keeping the prompt cache warm.
  • agent.override(deps=fake) swaps deps in tests.

Never

build instructions from untrusted text: they carry operator authority.

Pydantic AI Field Guide · Core agent · docs/dependencies.md, docs/agent.md#instructions

Dependency injection is how tools reach the outside world without globals. Declare deps_type on the agent, usually a dataclass, pass deps= on each run, and read ctx.deps in instructions, tools, output validators and hooks. deps_type is only used for type checking. Prefer async tools for I/O, because sync functions run in a thread pool. Instructions come in three forms: static on the Agent, dynamic with the @agent.instructions decorator (re-evaluated before every model request), and per run with run(instructions=...). Only the current agent’s instructions are sent, which matters in multi-agent setups. system_prompt, by contrast, is stored in message history and replayed on later runs. Use @agent.instructions(name='date', on_change='append') for state that changes mid-conversation: the change is appended as an InstructionDeltaPart instead of rewriting the start of the prompt, so prompt caching survives. TemplateStr('Hi {{name}}') renders fields from deps. Real-world use: the bank_support example looks up the customer name from a DB in dynamic instructions.
