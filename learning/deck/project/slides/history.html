02 · Core agent

Conversations carry history, usage and approvals

r1 = agent.run_sync('Tell me a joke.')
r2 = agent.run_sync('Why?', conversation=r1.conversation)
r3 = agent.run_sync('Explain?',  # switch model mid-chat
    message_history=r1.new_messages(),
    model='anthropic:claude-sonnet-5-5')

# persist and restore with full fidelity
blob = ConversationTypeAdapter.dump_json(r1.conversation)
conv = ConversationTypeAdapter.validate_json(blob)

async def chat(store, cid: str, prompt: str) -> str:
    conv = (await store.load(cid)
            or Conversation(conversation_id=cid))
    result = await agent.run(prompt, conversation=conv)
    await store.save(result)  # appends new messages
    return result.output

  • History is model-agnostic: start on one provider, continue on another.
  • ProcessHistory(fn) trims, redacts or compacts before every request.
  • ctx.enqueue() injects messages mid-run, e.g. a user typing while tools work.
  • History from a client can forge tool calls: sanitize_messages() it.

Pydantic AI Field Guide · Core agent · docs/message-history.md, docs/persistence.md

Each run produces ModelRequest and ModelResponse messages. result.all_messages() and new_messages() return them, with _json variants for storage. In version 2, prefer conversation=result.conversation over message_history: a Conversation bundles the messages with usage, the conversation ID and any pending deferred tool calls, so limits and approvals survive across turns. conversation_id='new' forks. ModelMessagesTypeAdapter and ConversationTypeAdapter round-trip everything. ConversationStore adds append-only saves, conflict detection, per-owner scope, branch and fork; InMemoryConversationStore is for tests, and a jsonb column is plenty in production. History processors are now the ProcessHistory capability (the old history_processors= kwarg is gone); ctx.context_window_used tells you how full the context is, which is handy for compacting at about 80 percent. Gotchas: when history is passed, no new system prompt is added; never mutate messages in place; a conversation ID is a key, not a credential, so check access. The chat_app example stores history in SQLite between requests.
